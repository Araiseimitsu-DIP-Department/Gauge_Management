# 貸出IDの採番不整合

## 確認できた原因と経路

2026-10-13の登録ログは主キー違反 `id=33834`。読取調査時の最大IDは33836、シーケンスのlast_valueは33834・is_called=trueで、次候補33835も既存行と衝突した。
現在のアプリはINSERTでidを指定せず、DBの自動採番を使用している。
実DBの列定義はIDENTITYではなく、関連付けられたシーケンスを `DEFAULT nextval(...)` で呼ぶ構成。自動採番として動作し、今回その定義自体は変更していない。

確定した発生経路:

- Git履歴db640ae以前のアプリは `MAX(id)+1` をINSERTで明示指定していた。シーケンスを進めない方式だった。
- `docs/pingauge_management_db/migrate_access_to_postgres_pingauge_management_db.py` の `--append-missing` はAccessのIDを明示して追記し、追記後の採番同期がなかった。
- 新規移行用スクリプトはAccess COUNTERをBIGINTへ移す仕様。自動採番の後付け時には、既存IDとの整合が必要。
- 現行 `scripts/migrate_access_to_postgres.py` とCSVテンプレートには補正があったが、従来のsetvalは採番値を戻し得て、通常のトランザクション巻戻しでは補正値を復旧できなかった。

今回どの経路・操作日時・実行者がずれを作ったかは未確定。DBの独自トリガーはなく、監査関連拡張も確認できなかった。過去の実行を示す追加ログは入手できていない。
正常な自動採番だけなら進んだ値を再使用しないため、ID明示投入または採番値の変更・復元を含む経路を確認する必要がある。

## 対応仕様

`scripts/postgres_sequence.py` で採番の確認・補正を共通化する。
対象テーブルをSHARE ROW EXCLUSIVEでロックし、シーケンスにも同じCACHE設定のALTERでロックを取得してから再読込する。
増分1・循環なしの場合だけ、次回IDが既存最大ID以下なら最大ID+1へ進める。進んでいる採番値は戻さない。
補正は `ALTER SEQUENCE ... RESTART WITH` を用い、呼出元のトランザクション失敗時に巻き戻せる。ロック待ちは5秒で停止する。
既存レコード・列定義・主キー・Access実装は変更しない。

通常移行と不足行追記は、データ投入と採番同期を同一トランザクションで実施する。
旧BIGINTだけのテーブルへの追記は従来どおり保持し、自動採番がない場合は警告する。自動採番を推測で後付けしない。
CSVテンプレートも投入と補正を一つのトランザクションにし、採番値を後戻りさせない。
SQL処理中の主キー違反を接続失敗として包んでいた接続コンテキストは、実際の接続失敗だけを接続エラーとする。

## 運用上の再発防止

旧版アプリ、手動SQL、TablePlusなどからIDを明示して投入した場合は、投入完了後に確認・補正を行う。
古いアプリや未修正の移行ツールを使い続けると再発し得る。通常登録にはDB採番を使う現行版を使用する。
確認だけなら:

```powershell
.\.venv\Scripts\python.exe scripts\repair_loan_sequence.py
```

補正は対象と影響への承認後にのみ実行する:

```powershell
.\.venv\Scripts\python.exe scripts\repair_loan_sequence.py --apply
```

`.env` のPostgreSQL設定を利用し、補正前後で貸出テーブルの件数・最大ID・全行ハッシュを比較する。
シーケンスは進める方向だけを補正し、既存業務データは変更しない。
ロック待ちや権限不足で停止した場合は、登録・移行処理を確認してから再実行する。
